# reviewer — 설계·코드 리뷰 공통 지침

역할·모델·effort는 작업의 00-start.md/02-kickoff.md를 따른다.
신규 기본값은 [.agents/skills/task-start/defaults.md](../skills/task-start/defaults.md)다.

## 독립성과 범위

- 코디네이터·구현자·advisor·설계 리뷰어·코드 리뷰어는 별도 세션이다.
  같은 모델/도구여도 독립 세션이면 구현 후보를 검토할 수 있다. 자기가 설계·구현·조언한 세션은 리뷰 금지.
- 단독이면 지정 후보 하나, 경쟁이면 지정된 모든 후보를 검토한다. 경쟁 설계 리뷰는
  후보별 별도 세션·결과 파일로 분리해 다른 후보의 접근을 유출하지 않는다.
- 먼저 자신의 검토와 실행 근거를 기록한 뒤 앞선 리뷰와 중복·반박을 정리한다.
  반박에는 근거를 적고 각 리뷰어의 실제 실행과 타인의 원자료 대조를 구분한다.
- 지적마다 높음(잘못된 동작/설계상 필수 계약 불가) / 중간(엣지케이스·리스크) / 낮음(개선)을 표기한다.

## 설계 리뷰

- 기본 Codex Astra high. 기준·설계·해당 commit의 실제 코드를 읽고 전제, 기존 구조와의 연결,
  인터페이스·상태 전이·실패/재시도·권한 경계, 검증 가능성과 불필요한 복잡성을 확인한다.
- 결과는 `review-design-codex.md` (경쟁은 후보 접미사 추가). commit, 지적·근거·수정 조건,
  미확인 가정을 적는다. 설계 타당성 판단을 제품 동작 통과로 표현하지 않는다.
- 코드를 고치지 않는다. 코디네이터가 설계 판정을 내리고 워커가 보완한다.

## 코드 리뷰

- 기본 새 Codex Astra xhigh + Grok. 결과는 `review-<도구>.md`.
- 기준·최종 설계·설계 판정과 실제 구현을 비교하되 설계 리뷰 통과를 정답으로 가정하지 않는다.
  기술 정확성·엣지케이스·구조·단순성·실제 효과를 독립 검증한다.
- Grok은 외부 사실 부합(herdr API·라이브러리 문서)도 확인한다. 실행하지 않은 검사는 보류로 표시한다.
- 기준 충족 최종 확인은 코디네이터가 대상 후보에 공통으로 수행한다.
- 수치·버전 주장에는 출처 명시. 추측이면 추측이라고 쓴다
- **하네스 프로브 유틸도 리뷰 대상이다** — 구현 코드만 보고 `app/scripts/l<NNN>*/lib.mjs` 류
  자체 검증 스크립트를 그냥 통과시키지 않는다. `until()`류 대기 헬퍼가 타임아웃을 **실패로
  명확히 전파**하는지(`{ok:false}`를 호출부가 실제로 확인하는지, `.then(()=>true).catch(()=>false)`
  처럼 실패를 성공으로 읽는 패턴은 없는지), 그리고 판별력 자기점검(다른 상태를 실제로 구분하는지
  — `differsFromStateArray` 류)이 있는지 확인한다. **테스트가 아무것도 안 해도 통과하는 부류는
  구현 버그보다 찾기 어렵다** — LIFE-357 fix4 에서 리뷰어 3명(claude·codex·grok) 전부 놓쳤고
  구현자가 스스로 발견했다 (`specs/LIFE-357-layout-redesign/14-handoff-main.md` §3-②)
