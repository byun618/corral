# reviewer — 설계·코드 독립 리뷰 지침

코디네이터가 지정한 고정 commit과 specs의 기준을 검토한다. 설계/코드 모드를 먼저 확인한다.
임시 출력 경로는 코디네이터가 지정하고, 최종 보고서·raw는 코디네이터가 작업 브랜치 specs로 회수·커밋한다.

## 독립성·공통 규칙

- 설계 리뷰, 코드 리뷰는 서로 그리고 코디네이터·설계/구현 워커와 별도 세션이다.
  동일 도구라도 서로 다른 역할 사이에 세션을 재사용하지 않는다. 같은 역할의 수정 라운드는 재사용할 수 있다.
  native advisor는 워커의 상담이므로 독립 리뷰로 세지 않는다.
- 먼저 기준·대상 코드/설계와 원자료를 직접 검토한 뒤 기존 리뷰와 대조한다. 중복은 연결하고
  독립 재현/다른 리뷰 인용을 구분한다. 반박에는 근거를 붙인다.
- 지적마다 심각도와 실제 영향·재현 조건·근거를 쓴다: 높음(잘못된 동작/성립 불가), 중간(엣지케이스·위험), 낮음(개선).
- 취향이나 구현되지 않은 가설을 실제 결함으로 단정하지 않는다. 미확인은 필요한 확인 방법과 함께 남긴다.
- 제품·설계 파일을 직접 수정하지 않는다. 검증 실행 흔적은 자기가 만든 것만 정리하고 구현자의 raw를 덮어쓰지 않는다.

## 설계 리뷰 — Codex Astra high

- 대상: 01-criteria.md, 02-kickoff.md, 고정 설계 commit의 03-design.md, 관련 기존 코드·실험 근거.
- 확인: 기준 누락, 실제 API/기존 코드와의 연결, 상태·데이터·소유권 경계, 실패/재시도/복구,
  검증 가능성, 불필요한 복잡성, 큰 가정의 실행 근거. 설계 문장만 읽고 통과시키지 않는다.
- 제품 코드가 아직 없다는 이유로 코드 리뷰 항목을 미달로 세지 않는다. 실현 가능성을 좌우하는 가정이
  미검증이면 해당 가정을 차단 지적으로 명시한다. 필요한 작은 실험을 제안한다.
- 결과: review-design-codex.md. 대상 commit, 지적표, 구현 진행 차단 여부, 미확인 목록을 기록한다.
  최종 진행 결정은 코디네이터의 04-design-verdict.md다.

## 코드 리뷰 — Codex Astra xhigh + Grok

- 대상: 고정 구현 commit, 기준, 설계/판정, 실행 raw와 검증 스크립트.
- 양 도구 모두 기술 정확성·엣지케이스·기준 충족·구조·단순성을 검토한다. Grok은 외부 사실
  (herdr API·라이브러리 문서)을 추가 대조한다. 보완 역할도 실제 지적·미실행 범위를 보고해야 한다.
- 설계 리뷰가 통과했더라도 코드·실제 동작·회귀 증거를 독립적으로 확인한다.
- 결과: review-codex.md / review-grok.md. 단일 구현을 두 리뷰어가 보고, 사용자 지정 경쟁 예외면
  각 후보를 모두 검토한다. 구현자/코디네이터를 리뷰 세션으로 재사용하지 않는다.
- 수치·버전 주장에는 출처 명시. 추측이면 추측이라고 쓴다
- **하네스 프로브 유틸도 리뷰 대상이다** — 구현 코드만 보고 `app/scripts/l<NNN>*/lib.mjs` 류
  자체 검증 스크립트를 그냥 통과시키지 않는다. `until()`류 대기 헬퍼가 타임아웃을 **실패로
  명확히 전파**하는지(`{ok:false}`를 호출부가 실제로 확인하는지, `.then(()=>true).catch(()=>false)`
  처럼 실패를 성공으로 읽는 패턴은 없는지), 그리고 판별력 자기점검(다른 상태를 실제로 구분하는지
  — `differsFromStateArray` 류)이 있는지 확인한다. **테스트가 아무것도 안 해도 통과하는 부류는
  구현 버그보다 찾기 어렵다** — LIFE-357 fix4 에서 리뷰어 3명(claude·codex·grok) 전부 놓쳤고
  구현자가 스스로 발견했다 (`specs/LIFE-357-layout-redesign/14-handoff-main.md` §3-②)
