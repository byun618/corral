# reviewer — 3자 리뷰 공통 지침

대상: specs/LIFE-NNN-*/ 의 경쟁 구현 브랜치들. 리뷰 결과는 specs/LIFE-NNN-*/review-<자기도구>.md 로 저장.

## 규칙

- 지적마다 심각도 표기: 높음(잘못된 동작) / 중간(엣지케이스·리스크) / 낮음(스타일·개선)
- 앞선 리뷰 파일을 먼저 읽고 중복 지적 금지, 반박은 허용 (반박 시 근거 명시)
- 검토 범위: 대상 브랜치를 전 관점으로 본다 — 기술 정확성·엣지케이스,
  판정 기준(01-criteria.md) 충족, 구조·단순성. 관점을 도구에 고정하지 않는다
- grok 은 위에 더해 외부 사실 부합(herdr API·라이브러리 최신 문서)을 반드시 포함
- 자기가 구현한 브랜치는 리뷰하지 않는다 — claude 리뷰어는 codex 브랜치를,
  codex 리뷰어는 claude 브랜치를 본다. grok 은 양쪽 다
- **모든 리뷰어는 도구와 무관하게 코디네이터·구현자와 별도 세션**으로 기동한다.
  같은 도구를 쓴다는 이유로 코디네이터나 구현 세션을 리뷰어로 재사용하지 않는다.
- **단독 구현이면 셋 다 그 한 브랜치를 본다.** 구현자와 같은 도구의 리뷰어도 새 세션이어야 한다
  (LIFE-344의 독립성 원칙을 Claude·Codex 코디네이터 양쪽에 적용).
- codex 리뷰어는 `codex -c model_reasoning_effort=xhigh` 로 기동한다 — 검증은 생성보다 쉬워
  구독 기본 모델로도 적대적 리뷰어 역할을 충분히 한다 (구현 쪽 플래그십 페어링과 급을 맞출 필요 없음 —
  버전명은 자꾸 바뀌므로 여기 박지 않는다, 2026-09-18)
- 기준 충족 최종 확인은 판정 단계에서 양 브랜치에 공통으로 한 번 더 수행된다
- 수치·버전 주장에는 출처 명시. 추측이면 추측이라고 쓴다
- **하네스 프로브 유틸도 리뷰 대상이다** — 구현 코드만 보고 `app/scripts/l<NNN>*/lib.mjs` 류
  자체 검증 스크립트를 그냥 통과시키지 않는다. `until()`류 대기 헬퍼가 타임아웃을 **실패로
  명확히 전파**하는지(`{ok:false}`를 호출부가 실제로 확인하는지, `.then(()=>true).catch(()=>false)`
  처럼 실패를 성공으로 읽는 패턴은 없는지), 그리고 판별력 자기점검(다른 상태를 실제로 구분하는지
  — `differsFromStateArray` 류)이 있는지 확인한다. **테스트가 아무것도 안 해도 통과하는 부류는
  구현 버그보다 찾기 어렵다** — LIFE-357 fix4 에서 리뷰어 3명(claude·codex·grok) 전부 놓쳤고
  구현자가 스스로 발견했다 (`specs/LIFE-357-layout-redesign/14-handoff-main.md` §3-②)
