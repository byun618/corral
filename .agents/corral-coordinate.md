# corral — 코디 전용 규칙 (task-coordinate 보충)

paddock 의 task-coordinate 에 없는 이 프로젝트 규칙. 옛 task-coordinate SKILL.md·implementation.md 에서 원문 그대로 옮겼다(2026-11-24 adopt).
코디는 분석(§1) 전에 한 번 읽는다. 절 번호는 옛 스킬 기준이다.

## 분석·판정 기준

- **선행 문서의 사실 주장을 대조표로 검증한다** — 일감 본문·00-project.md 의 전제가 틀렸을 수 있다.
  산출물: `00-analysis.md` (+ 외부 서치 원문 `00-analysis-grok.md`)
- **UI 비중이 큰 일감이면 `design-brief`/`design-intake` 삽입 여부를 검토한다** — 비주얼 디테일이 판정
  기준에 안 잡히면 목업 없이 구현자 재량에 맡길 때 재작업 위험이 있다.
  넣으면 `corral-specs/app-screens.md`(없으면 먼저) → `design-brief` → 외부 Claude Design → `design-intake` →
  그 결과로 `01-criteria.md`/`02-kickoff.md` freeze. 안 넣으면 사유를 `00-analysis.md` 에 한 줄 (판단 없이 생략 금지)
- **신호를 좁히거나 조건을 거는 일감은 그 신호를 읽는 소비자를 코드로 전부 열거하고 소비자마다 그대로/바뀜/따로 보호를 칸에 적는다**
  (함수 호출처만이 아니라 대상 값의 리터럴 목록까지 — 새 신호를 더하기만 하면 해당 없음, 문서·스킬 일감은 참조 grep 으로 대신)(LIFE-683·708).
- **지연·경합 수정의 관문은 고친 경로(목표 순서)가 실제로 난 횟수를 로그로 따로 세어 증상 동작 결과와 짝지어 칸에 둔다** —
  다른 경로가 따라잡아도 통과로 보이므로 증상 통과만으로 수정 효과를 증명했다고 쓰지 않는다. 손으로 그 창을 못 맞히면 게이트 ⓪ 에서 공백을 합의한다(LIFE-710·595).
- **관측 대상이 데이터·상태(특정 pane·레인·목록)면 기준을 동결할 때 조회 명령과 결과를 기준에 붙이고, 없으면 대체 대상을 그 자리에서 정한다** —
  사후에 바꾼 대상의 값은 통과로 올리지 않는다. 구현 뒤에야 생기는 대상은 「구현 뒤 만드는 픽스처」로 적는다(LIFE-746·812).
- 빠른 확인 (옛 §2):
  문서·스킬 일감의 빠른 확인은 문구 대조만으로 끝내지 않는다 — 바뀐 명령 블록을 문서에서 그대로 추출해 정상·빈 입력·실패 분기를
  한 번씩 돌린다. 손으로 옮긴 복제본으로 대신하지 않는다(LIFE-713·683).

## 구현·리뷰

- **격리 기동이 헤드리스라 안 된다고 단정하지 않는다** — 필요한 것은 TTY 이고 `script(1)` 류 PTY 래퍼로 띄울 수 있다.
  기동 경로에 따라 시간이 자릿수로 갈리므로(탭 경로 수십 초 · PTY 경로 수십 ms) 재기동 시간이 통과선이면 경로를 적는다.
- 게이트 ⓪ 보고의 진행 방식 줄 (옛 §3) — 디자인 브리프 삽입 여부와 사유를 함께 보고한다:
  - **진행 방식**: 단독 구현(또는 경쟁 발동 근거), 역할별 모델/effort·advisor, 디자인 브리프 삽입 여부와 사유
- 코드 리뷰 (옛 §5):
  **첫 리뷰어를 띄우기 직전에 LA 「검증 중」 전이를 확인한다** — 절 머리의 전이는 이 자리에서 한다. (LIFE-713·822·834)
  수정 diff 를 정독할 때 01-criteria 가 가리키는 정의 자리(문구·bullet)가 여전히 맞는지, 기준을 보강했으면 같은 항목의 기존 행과 문자 그대로 양립하는지도 대조한다. (LIFE-714·835)
- 구현 하네스 (옛 implementation.md 「구현 worktree 의 하네스」):
  옛 일감 하네스(LIFE-717 이전 코드 레포의 일감 번호 폴더)는 `corral-specs/LIFE-<번호>-*/scripts/<원래 폴더명>/`(원래 폴더명은 `l` 뒤에 일감 번호)에 있고,
  폴더별 색인과 돌리는 커밋·worktree 만드는 법은 LIFE-717 작업 폴더(`…-script-cleanup`) 루트 `moved-index.md` 「재현」에 있다.
  옛 하네스 가운데 기본 출력이 worktree 안 `specs/…` 인 것을 돌릴 때는 출력 경로를 작업 폴더로 지정하게 한다
  (거기 남은 파일은 `task-finish.sh` 가 정리 전에 멈춰 알린다).
- **재사용 배달 직전 — 그리고 pane 에 글을 넣는 모든 경우(질의 답 주입 포함) — 『화면 관측』을 따로 하고 입력줄이 비었는지 본다.** 읽기와 주입을 한 명령에 묶지 않는다. 글이 있으면 배달하지 않고 그 글을 보여 사용자에게 묻는다(제안이 직전 코디 본문과 같은 문장이면 기록 대조로 갈음) —
  배달이 덮어쓰면 사람이 쳐 둔 미제출 글은 복구할 길이 없다. Claude Code 가 입력줄에 그리는 다음 입력 제안도 화면으로는 같은 모양이므로
  같이 묻는다(제안은 Enter 만으로 제출되지 않는다 — 사용자가 제안이라 하면 『본문 주입』으로 배달한다). 『화면 관측』이 공백인 매핑은
  재사용 배달 대신 새 기동을 쓴다(LIFE-724·683·745·746).

## 기록·PR·출고

- 게이트 ② 기록 (옛 §8) — devlog 는 paddock 의 두 절 대신 이 형식을 쓴다:
  - **devlog** `devlog.md` (비공개) — 한 파일, 날짜별 절(`## YYYY-MM-DD`). 날짜마다 세 관점:
    **사람**(그날의 결정·승인·지시 원문 — LLM 초안이고 사용자가 고친다. 감정·의도를 추측해 쓰지 않는다) ·
    **LLM**(시도 → 실패 → 원인 → 해결) · **LLM 이 본 지시**(방향을 바꾼 지시, 반복된 지적, 모호했던 지시).
    끝에 **회고** 절 — 일감 전체를 세 렌즈로 본다: 문제 정의(처음 정의가 맞았나) · 검증 설계(기준·관문이 결함을 잡았나) ·
    방식 개선(다음엔 무엇을 바꾸나). 관점은 누구의 시선이고 렌즈는 무엇을 보나다.
  - devlog 재료: 코디 기억이 1차지만 compact 로 초반이 뭉개진다 — 날짜·사실은 코디 세션 transcript 와 git log(작업 브랜치·corral-specs)로 대조한다.
    `reviews.md` 는 내용 대조에 쓴다 — 시각이 드물어 날짜 축이 되지 못한다.
    - **코디 세션 기록 찾기**: `00-start.md` 에 시작 세션이 적은 세션 기록 경로(task-start 4단계 — 『세션 기동』 응답이 돌려준 값)를 쓴다.
      코디가 재기동돼 경로가 여럿이면 날짜순으로 모두 읽는다.
      경로가 없으면(기동 응답에 경로를 주지 않는 도구 — 지금 corral 매핑의 Codex 코디, 매핑 『세션 기동』 절 — 또는 그 기록을 남기기 전에
      시작한 일감) 경로를 짐작하지 않고(능력 계약 H6) devlog 에 「코디 기록 없음」을 적은 뒤 코디 기억·git log 로만 쓴다.
      즉 transcript 대조는 지금 Claude 코디 일감에서만 된다.
- PR 본문 `pr.md` (옛 §8):
       코드 레포가 공개될 수 있으므로 원자료 경로·내부 세션 정보를 본문에 옮기지 않는다. 출고 때 릴리즈 노트가 이 본문을 재료로 쓴다.
- PR 생성 뒤 보고 (옛 §8):
  4. 사용자에게 스크립트 출력 원문과 함께 **PR 번호(묶음 자식은 feature 반영 결과)**, 인계 문서 경로
     `corral-specs/LIFE-NNN-<슬러그>/handoff-main.md`(절대경로) 를 보고하고 "PR 생성·정리 완료, 출고 대기"라고 끝낸다.
     열린 PR 이 3~4건을 넘거나 같은 파일을 건드리면 출고를 권한다. LA 는 `검증 중` 그대로다.
- 스크립트가 실패하면 멈추고 원문을 보고한다. 이미 연 PR 은 `task-pr.sh` 재실행이 재사용하고, 남은 정리는 같은 명령으로 이어 간다(멱등).
- 코디네이터가 직접 실행하는 것은 PR 생성과 정리까지다. **출고**(release 브랜치에 PR 모으기·main 머지·태그·릴리즈 노트·dmg·APK·LA 완료)는 본체 세션의 `release` 스킬 몫이다.
  작업 관문에서 만든 브랜치 dmg·APK 는 dev 빌드다 — 정식본은 출고 태그에서 만들고, 폰의 브랜치 APK 도 출고 때 태그 APK 로 덮인다.
