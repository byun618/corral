## 절차의 기록·훑기 줄은 「언제 커밋되나」·「무엇이 걸리나」를 먼저

- **Scope:** `.agents/skills/**` 문구 작성
- **Learning:** 기록 지시는 그 단계의 커밋 시점 뒤에 놓이면 실행되지 않는다(전달 뒤 수정 금지 같은 규칙과 부딪힌다). 「폴더를 glob 으로 훑으라」는 같은 모양의 README·예시까지 걸리므로, 대상을 이름으로 좁혀 쓴다.
- **Evidence:** LIFE-704 리뷰 r3 — 경로 기록 줄이 전달 뒤 단계에 있어 실제 흐름에서 비었다. 최종 관문 리허설 — Last reviewed 훑기에 README 형식 예시가 걸렸다.
- **Disposition:** 스킬 작성 체크리스트가 생기면 그곳.

## 열린 「어긋남 0」 항목은 대상과 문턱을 박는다

- **Scope:** task-coordinate §2 판정 기준, 새 독자 리허설 채점표
- **Learning:** 「어긋나 보이는 곳이 있는가」 같은 열린 공통 항목은 고칠 때마다 독자가 새 경미 지적을 찾아 통과선이 움직인다. 대상(바뀐 줄과 그 줄이 가리키는 절)과 심각도 문턱(따른 행동이 달라지는가)을 기준에 박는다.
- **Evidence:** LIFE-719 — 리허설 세 회차가 시나리오는 모두 맞혔는데 공통 항목은 매번 미달이었다. 앞 지적의 수정이 새 경미 지적을 만들었다.
- **Disposition:** task-coordinate §2 판정 기준 작성 줄 — 다시 나면.

## 기준 칸이 진입 경로를 열거하면 각 경로의 base 동작을 코드 위치로 대조한다

- **Scope:** task-coordinate §2
- **Learning:** 통과선에 「A·B·C 를 누르면 X」처럼 진입 경로를 나열할 때, 각 경로가 base 에서 실제로 무엇을 하는지 파일:줄로 확인해 칸에 붙인다. 확인 없이 나열한 경로는 구현이 지키지 못하는 기준이 되거나 범위 밖 동작 변경을 부른다. 열거는 함수 호출처만이 아니라 대상 값의 리터럴 목록(고정 배열·`as const`)까지 훑는다 — 런타임 등록이면 등록 지점을 훑는다. 통과선이 특정 화면 상태(빈 영역 등)를 전제하면 그 상태가 모델에서 존재할 수 있는지, base 에 그 상태를 만드는 경로가 있는지도 본다.
- **Evidence:** LIFE-682 — 「작업 중 줄」은 base 부터 다른 동작이라 판정에서 보류됐고 게이트 ① 에서 기준을 정정했다. LIFE-520 — 분석이 함수 호출처만 모아 리터럴 목록을 쓰는 진입점 둘(메뉴·팔레트)이 리뷰 두 라운드에 걸쳐 나왔다. LIFE-823 — 「빈 영역 가장자리 = 분할」이 빈 영역을 접는 규칙과 맞지 않아 기준을 고쳤고 관문 칸도 공백이 됐다.
- **Disposition:** task-coordinate §2 기준 작성 줄 — 다시 나면.

## 통과선에 경로·파일 속성을 박을 때는 그 자리에서 실물을 본다

- **Scope:** task-coordinate §2 판정 기준(정정 포함)
- **Learning:** 기준에 경로·심링크·realpath·권한을 적을 때는 쓰는 그 자리에서 `ls -l`·realpath 로 확인한다. 기억이나 다른 문서의 경로 문자열로 쓴 조건은 어떤 구현도 못 맞추는 통과선이 된다.
- **Evidence:** LIFE-520 — 「realpath 가 설치 폴더 아래」를 박았는데 설치기가 그 자리에 다른 폴더로 가는 심링크를 두어 늘 미달, 워커가 통과선을 안 바꾸고 올려 정정했다.
- **Disposition:** task-coordinate §2 기준 작성 줄 — 다시 나면.

## 짧은 사용자 원문은 일감에 박기 전에 해석을 되묻는다

- **Scope:** task-start 일감 본문 작성, task-coordinate §1
- **Learning:** 원문이 짧고 UI 용어(툴바·툴팁·메뉴·패널)가 겹치면 「X 를 Y 로 읽었다」 한 줄로 되묻고 본문에 박는다. 틀린 해석으로 분석·관측 질문까지 내려가면 비용이 통째로 버려진다.
- **Evidence:** LIFE-755 — 「머리 줄 툴바가 안 떠」를 섹션 머리 hover 툴바로 읽어 분석·질문 2개를 한 뒤 사용자 정정(아이콘 이름 툴팁)으로 다시 잡았다.
- **Disposition:** task-start 일감 본문 작성 단계 — 다시 나면.

## 폰 손 넘김은 코디가 시험 채널을 만들고 지시를 주입한다

- **Scope:** 모바일 네이티브 관문의 손 넘김 체크리스트, task-coordinate §5 최종 관문
- **Learning:** 폰 앱은 새 채널을 못 열고 사용자 손은 제스처 하나에 집중해야 하므로, 코디가 시험용 에이전트 pane 을 만들고 회차마다 구분 줄을 찍은 뒤 지연 답 지시를 주입한다. 사용자는 손 동작과 한 줄 결과만 말하고, 회차 안내에 답까지 남은 시간을 적는다.
- **Evidence:** LIFE-595 — 코디 주입으로 바꾼 뒤 12회가 매끄럽게 돌았다.
- **Disposition:** 모바일 관문 체크리스트 형식(작업 폴더 템플릿 또는 task-coordinate §5) — 다시 나면.

## 원자료 폴더에 임시 git 저장소를 옮기지 않는다

- **Scope:** 리뷰어 일감 명세, corral-specs 커밋
- **Learning:** 재현용 임시 저장소는 출력만 텍스트로 옮긴다. 폴더째 옮기면 `git add` 가 gitlink 를 만든다. 커밋 전에 gitlink 수를 본다.
- **Evidence:** LIFE-575 — 리뷰 원자료가 gitlink 로 커밋돼 되돌렸다.
- **Disposition:** `.agents/rules/validation.md` 「원자료 보관」 — 다시 나면.

## 공용 알림 통로를 더 자주 쓰는 변경은 그 통로의 수명·배치를 기준에 넣는다

- **Scope:** task-coordinate §2 판정 기준
- **Learning:** 새 조작이 기존 안내·알림 통로로 결과를 알리면 그 통로의 수명(언제 지워지나)·배치(넘침)가 새 빈도에서 결함으로 드러난다. 기준에 「맥락이 바뀌면 남지 않음·좁은 폭에서 레이아웃을 깨지 않음」을 같이 박는다.
- **Evidence:** LIFE-822 — 기준은 모두 통과했지만 격리 GUI 캡처에서 안내가 맥락 변경 뒤 남고 좁은 영역에서 탭바를 덮었다.
- **Disposition:** task-coordinate §2 — 다시 나면.

## 새 입력 방식의 시작·끝 사용 모델은 기준 단계에서 참조 구현과 대조하고, 첫 사람 회차를 수렴 전에 둔다

- **Scope:** task-coordinate §2(판정 기준)·§4(구현 관문 층)
- **Learning:** 사용자가 새로 손에 익혀야 하는 입력 방식(단축키 홀드·토글, 음성 등)은 「언제 끝나고, 끝난 걸 어떻게 아나」를 기준에 박기 전에 참조 구현의 모드와 대조해 선택지로 사용자에게 묻는다. 리뷰는 기준 안의 결함만 잡으므로, 사용 모델 확인용 짧은 사람 회차를 첫 구현 직후에 둔다.
- **Evidence:** LIFE-834 — 토글 모델로 리뷰 r3 까지 수렴한 뒤 첫 사람 회차에서 정지 모델이 뒤집혀 수정 네 라운드가 더 생겼다. 참조 구현에는 처음부터 홀드·자동 정지 모드가 있었다.
- **Disposition:** task-coordinate §2 한 줄 — 다시 나면. 안 통하는 자리: 기존 동작을 고치는 일감·문서 일감·경량 경로.
