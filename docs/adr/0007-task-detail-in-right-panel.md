# 작업 상세는 오른쪽 패널의 한 보기 — 작업 페이지를 앱 시작부터 마운트하고 상세 노드를 옮긴다

## Context and Problem Statement

작업 상세가 작업 페이지 안 aside 라 보드 폭을 차지했고, 페이지를 닫으면 상세도 사라졌다. LIFE-682 는 상세를 페이지와 무관한 전역 오른쪽 패널의 보기로 옮기기로 했다. 상세 상태(선택·쓰기 잠금·늦은 응답·되돌리기 정합화)는 작업 페이지 훅에 깊게 얽혀 있었다 — 이 상태를 어디에 두고 상세를 어떻게 패널에 그릴 것인가.

## Decision Drivers

* 쓰기 정합화 경로(LIFE-622/623/632)를 옮기다 놓치는 위험을 피한다.
* 작업 페이지를 열지 않은 앱 시작 직후에도 상세를 복원·편집할 수 있어야 한다.
* 상세는 보일 때만 읽는다 — 새 폴링 금지.
* 패널 상세 ↔ 작업 페이지 전체 모드를 오가도 입력 초안·포커스가 유지돼야 한다(이중 마운트 금지).

## Considered Options

* 상세 상태를 App 으로 올린다
* 공용 provider 로 뺀다
* 작업 페이지를 앱 시작부터 (닫힌 채) 마운트하고, 상세는 안정된 host 노드에 portal 해 그 노드를 패널 자리 ↔ 전체 모드 자리로 옮긴다

## Decision Outcome

Chosen option: "작업 페이지 일찍 마운트 + host 노드 portal", because 상태 소유를 그대로 두어 쓰기 정합화 경로를 건드리지 않고, 작업 페이지의 목록 읽기는 이미 「열림」 조건이라 일찍 마운트해도 닫힌 페이지는 목록을 읽지 않으며, 노드 이동은 portal 대상을 바꾸지 않아 리마운트가 없다.

### Consequences

* Good, because 상세 내용·필드 동작·쓰기 경로가 그대로이고 기존 시험은 렌더 하네스만 바꿔 통과했다.
* Good, because 마운트(선택이 있으면 유지)와 읽기(보일 때만)를 분리해 숨기기·보기 전환에도 초안이 남는다.
* Bad, because 숨긴 상세가 마운트된 채 남아 「보일 때만」 이어야 할 효과(링크 재조회·Esc·포커스)를 하나씩 보임 조건으로 막아야 한다 — 새 효과를 더할 때마다 같은 질문이 생긴다.
* Bad, because 닫힌 작업 페이지 안 모달(시작·만들기)이 터미널 화면에서도 떠서, 앱 단축키·터미널 포커스 차단을 페이지가 App 에 알려야 한다.
* Bad, because 앱 시작 때 작업 페이지가 설정 읽기(기존 IPC)를 한다.

### Confirmation

`TasksPage.l682` 시험(닫힌 페이지 목록 읽기 0 · 숨긴 상세 단건 읽기 0 · 같은 aside 노드 이동 · 초안 유지 · Esc 사슬) · 리뷰의 상태 경계 초점 · 격리 관문 A5·A7.

## Pros and Cons of the Options

### 상세 상태를 App 으로 올린다

* Good, because 소유가 패널 쪽과 같은 층이라 구조가 단순해 보인다.
* Bad, because `useTaskDetail` 이 작업 페이지의 쓰기 원장(잠금·늦은 답·되돌리기)에 기대 그 정합화를 통째로 옮겨야 한다.

### 공용 provider 로 뺀다

* Good, because 페이지·패널 어디서나 같은 상태를 읽는다.
* Bad, because App 으로 올리기와 같은 수술이 필요하고 provider 경계가 하나 더 생긴다.
